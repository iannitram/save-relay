# Installer hub: game-file downloads (design)

Status: **Dropbox, Nextcloud and Google Drive sources implemented for the mobile C interface** (#305, #309, for Uncharted-Universal#523): `src/gamefiles/` is the core, `Dropbox`, `WebDav` (Nextcloud) and `Drive` are its `GameSource`s, and `save_relay_game_files_*` in `include/save_relay.h` (with the Swift and Kotlin wrappers) is the interface; `save-relay game-files` is the command line. The explicit legacy mapping and the two #324 compatibility functions run over the same engine (#309). Fake-service and local-server tests back all three sources. A real-Nextcloud game-files check (Nextcloud 33 only) is a step of the Linux integration leg in CI; it has not yet run in CI, because that step is new on this branch. No real Dropbox or Drive account check exists. Pause as a state apart from cancel and handle-based sessions (#309, #310) are not built; see "What is implemented" at the end. Save Relay remains the save-sync application; the planned installer also downloads the user's prepared app or game files. A thin game app asks before starting the download. No game data, account credentials or private manifests belong in this repository, a release, or a public server.

## Scope and layout

Use the service and credential store already configured on this machine: Nextcloud, Dropbox or Google Drive. No second sign-in or wider OAuth scope is required by this design. Asset operations are independent of save sync, its revisions, retention, conflict resolution and locks. The service files root contains the existing configured save root and a separate `game-files/<app-id>/` tree. Never interpret a save tree as assets or delete or overwrite save data. For explicitly configured legacy apps, an app-supplied trusted mapping may instead select a fixed provider-relative root and put files directly beneath it; never accept that root from a remote manifest. An app ID is a single portable identifier (`[a-z0-9][a-z0-9._-]*`, at most 128 ASCII bytes, excluding `.` and `..`). Each app has a manifest `game-files/<app-id>/manifest.json` and its payload files below `game-files/<app-id>/files/`. The owner prepares and makes these files accessible; this design does not implement upload, discovery, piracy distribution, or public hosting.

Dropbox confines access to its registered App folder. Nextcloud uses the configured account's WebDAV files root and app password. Google Drive retains `drive.file`: the app can access files it created or that the user explicitly opens or shares with it via a supported picker. Merely putting files in My Drive, or granting access to a folder, must not be assumed to grant access to each existing descendant. An ingestion/upload or per-file picker flow for Drive is future work; until it exists, only already accessible files can be downloaded. No broad Drive scope is implied. Duplicate names or inaccessible/ambiguous paths fail visibly rather than picking an arbitrary file. [Google scope documentation](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) and [desktop/mobile Picker](https://developers.google.com/workspace/drive/picker/guides/desktop-mobile-picker) describe the access boundary.

## Manifest v1

UTF-8 JSON, bounded to 4 MiB before parsing, strict fields and no duplicate JSON keys. Example (illustrative digest only):

```json
{"version":1,"app_id":"example-game","files":[{"path":"data/example.bin","size":3,"sha256":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"}]}
```

`version` is integer 1, `app_id` equals the requested ID, and `files` is a nonempty array of at most 100,000 entries. `size` is an unsigned 64-bit integer; reject total-size overflow. `sha256` is exactly 64 lowercase hexadecimal characters of the complete file.

**Optional fields.** The only other fields are optional and defined; any unknown field is still refused. Top level: `build_id` and `nx_game_abi`, each 1 to 128 bytes of printable ASCII (space to `~`). They are publisher labels, carried in the parsed manifest (`Manifest::build_id`, `nx_game_abi`) and covered by the manifest digest because the digest is over the exact bytes; they do not change what is installed, and the plan and progress JSON do not report them yet. Per file: `exec`, a boolean, default `false`. On Unix the engine sets mode 0755 on the verified part immediately before the no-replace publication (so the final name never exists without it); an existing file adopted by hash gets the same mode when the manifest says `exec` (a copy that lost its mode bits still launches), and keeps its own mode otherwise. On Windows there is no execute bit and `exec` is ignored.

**Paths** are nonempty UTF-8 relative `/`-separated names, at most 4096 bytes overall and 255 bytes per segment. Reject empty segments, `.`, `..`, backslash, NUL and control characters, absolute paths, drive prefixes, trailing dot/space, reserved installer metadata names (`.save-relay*`), and the characters `< > : " | ? *`.

- *Windows reserved names*, decided on the folded segment, so case, width and superscripts do not matter: `CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `COM0` to `COM9` and `LPT0` to `LPT9` (the superscript digits `¹ ² ³` fold to `1 2 3`), with or without an extension, and with spaces before the extension (`NUL .txt`). Segments shaped like NTFS 8.3 short names (`LONGFI~1.BIN`) are not refused.
- *Collisions.* Every path is reduced to a key per segment: canonical decomposition (NFD), full Unicode default case folding (so `Straße` equals `STRASSE`, final sigma equals sigma, `ſ` equals `s`), then compatibility decomposition (NFKD) with the fold applied again, as the Unicode FAQ prescribes for a stable key. Two entries with one key, or an entry whose key is a folder prefix of another's, are `manifest_invalid`. This is stricter than each target it protects: NTFS and exFAT (upcase table, no normalization), APFS and HFS+ (normalization-insensitive, usually case-insensitive) and Android f2fs casefold (NFD plus full folding). It does not model locale tailoring (Turkish dotless i).
- *Device-owned paths*, refused in every layout and mode, on the same folded key (so `USER/x` and a decomposed spelling do not slip through): a first segment `user` or `config.ini`, and `root/user` and `root/config.ini` (each with anything below). The player's folder and settings are never part of a payload. Legacy mode additionally refuses a first segment `logs` and the path `manifest.json`.

Reject unknown fields and versions. The manifest itself must come from the configured service at the specified path, and its SHA-256 of exact bytes identifies a session; no manifest may specify another URL or filesystem root. For an explicitly configured legacy mapping only, accept a version-1 manifest without `app_id` (ACNH Android, and the Linux shape with `build_id` and `nx_game_abi`), binding the supplied app ID and fixed root into the session identity; apply all the same validation to its file entries. In standard and inline layouts `app_id` is required. A manifest hash verifies consistency during resume, not publisher authenticity. The owner must trust the source and prepared hashes.

## Range and identity contract

Use bounded chunks (initially 1 MiB maximum), never `Remote::get` for payloads. Extend the remote seam with a bounded range operation returning bytes plus total length and representation identity. Each HTTP request requests `bytes=start-end` and bounds response reading to the chunk limit, including when the server ignores Range. The host mobile transport must honor that bound too. Accept only an identity-encoded, single-part 206 whose `Content-Range` begins at the requested offset, ends within the request, reports the exact manifest size, and agrees with the actual nonzero body length. Reject 200, malformed/missing ranges, multipart, unexpected encoding, 416 before completion, mismatched size or excess data without appending. A smaller valid contiguous 206 is acceptable and advances only by its verified length. Empty files need no range request and are verified against the empty hash. Provider errors must not leak credentials or response bodies.

Bind each file to the provider identity observed at the start and across restart: compare Dropbox revision returned in every download response; send Nextcloud a strong ETag with `If-Match`; compare Drive file ID and version before and after each chunk. A detected change stops with `remote_changed` (class `retryable`) before that chunk is appended, and discards the file's partial copy. These checks do not prove that a representation never changed during a request: in particular a WebDAV ETag may repeat, and Drive metadata checks do not atomically bind media bytes. Therefore only exact final size and SHA-256 against the trusted manifest permit publication; a mixed or altered file fails integrity verification and is never installed. Resume requires the same observed identity, but identity alone is not an integrity guarantee. Drive revision-specific media reads can pin a revision only when it is retained as Keep Forever; do not require this for ordinary files. Drive blob downloads use `files.get?alt=media` and Range; Workspace exports do not support partial download. Nextcloud WebDAV uses HTTP GET and Range; servers ignoring or not supporting it fail as `range_unsupported`, never download an unbounded body. Dropbox content downloads use HTTP Range and their result metadata. See [Google downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [Nextcloud WebDAV operations](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html), [Dropbox content-download semantics](https://www.dropbox.com/developers/documentation/http/documentation#files-download), and [HTTP range semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests).

## Destination, checkpoint and publication

The caller supplies an app-private destination and a separate app-private state directory; neither can be the save directory or overlap the other. The core validates paths before any write and traverses directories without following symlinks or reparse points, including during creation and publication. This requires directory-handle-relative no-follow operations or an equivalent platform guarantee that prevents replacement races; a check followed by ordinary path-based open is insufficient. Refuse unsupported platforms safely. Refuse existing unrelated destination files and directories where ownership is not established; never overwrite them. Installer-owned completed files are skipped only after streaming size and hash verification. Replacement of an older installer-owned file needs an explicit update design; v1 reports a conflict instead of overwriting it.

Store each partial in the same filesystem as its eventual final file, in an installer-owned staging directory with collision-resistant names, exclusively created and never following links. A durable session record binds service/account identity without storing tokens, app ID, destination identity, exact manifest digest, each file's expected size/hash, provider identity and last durable offset. Serialize one writer per destination with an OS-backed lock held for the session; a crash releases it. No public API accepts arbitrary state or part paths. After each chunk, write at the expected offset, flush and fsync the part, then atomically write/fsync the checkpoint and parent directory. On restart truncate any bytes beyond the recorded durable offset, revalidate the record, path and provider identity, and hash the staged prefix before continuing. A crash between data sync and checkpoint may re-download at most one chunk; zero wasted bytes cannot be guaranteed. A record ahead of durable data, oversized part, missing identity, manifest change or invalid metadata fails closed rather than appending.

Once all bytes are present, stream SHA-256 over the whole part and compare exact size and digest. Fsync the part; publish using an atomic **no-replace** operation on the same filesystem, fsync the parent directory, then durably mark completion. If power fails after publication but before checkpoint, recovery verifies the final file before marking complete. Never remove or replace an unrelated final file. Keep partials on recoverable failures or pause; explicit cancel leaves completed files and removes only verified session-owned staging when the caller requests cleanup. Recheck existing completed files on every restart; a mismatch is a conflict, not an invitation to overwrite.

## Control and ABI plan

The portable Rust core runs one download at a time and reports app ID, state, completed/total files, durable/total bytes and current relative path. States are `running`, `complete`, `cancelled` and `error` (`ready` is the engine's state before its first step and is never left in the C progress). A cancel is resumable, so there is no separate `paused`. Network interruption is retryable without discarding the checkpoint. Errors are told apart by code (`reauth_needed`, `auth_failed` for a Nextcloud 401/403, `server_unreachable` for a dropped connection, `range_unsupported`, `remote_changed`, `integrity_failed`, `manifest_invalid`, `destination_conflict`, `io`, `busy`) and by `error.class`; tokens and private content are never logged.

#310 defines the mobile contract as **game-files interface version 1**. `include/save_relay.h` is the reference and `save_relay_game_files_version()` returns the number; the Kotlin (`SaveRelay.GAME_FILES_VERSION`, `gameFilesVersion()`) and Swift (`SaveRelay.gameFilesVersion`, `nativeGameFilesVersion()`) wrappers carry the same number, and `tests/ffi_bindings.rs` fails when the header, JNI shim, Kotlin and Swift disagree on functions, parameter counts or version. Within a version no signature, envelope command or error code changes.

- **Calls (all return the JSON envelope, freed with `save_relay_free`):** `save_relay_game_files_plan`, `_download`, `_progress`, `_cancel`, `_cleanup`, and the compatibility pair `save_relay_download_game_files` and `save_relay_game_files_status` (#324, wrappers over the same engine). There is no session handle: the download is process-wide, keyed by nothing, and the checkpoint on disk is the durable state, so closing the wrapper never erases resumable state.
- **Threading:** download (and the compatibility download and plan) block: the app calls them off the UI thread (a foreground service on Android, a background queue on iOS). Progress and cancel return at once and are called from other threads while a download runs. Any function may be called from any thread. The library creates no threads and schedules nothing; host apps own foreground and background execution, and call download again at the next launch or when the OS lets them run.
- **One download at a time per process:** a second download answers `busy` (class `retryable`) and does not disturb the running one. `cleanup` and `save_relay_init` answer `busy` while a download runs.
- **Cancel:** takes effect after the chunk in flight is made durable (the engine waits to retry in short slices that a cancel cuts short; no source sleeps inside a request, so a cancel waits for at most the request in flight); the download call returns state `cancelled` and a later download continues. A cancel reaches only the run that is running when it arrives (`data.running` true). Nothing running answers `running: false` and the cancel is not kept, so it can never leak onto a later run; an app that cancels a download it has only just handed to another thread keeps its own flag (or cancels again once progress shows the run). All of claim, cancel, cleanup and re-init take one lock, so none of them can interleave.
- **Progress:** a download sets `running` progress for its own app as soon as it has claimed the slot, so a poller never reads the previous run's `complete`; however a run ends (error before the engine reports, an engine error, or a panic caught at the C boundary) the progress is left `error`, never stuck `running`. Cleanup resets it to `null` under the same lock that keeps a download from starting.
- **Host lifetime:** the choice is to **refuse, not refcount**: `save_relay_init` answers `busy` and keeps the host while a download runs, so a running download always calls the host it started with. The wrappers add the rest: Kotlin `close()` cancels a running download and releases the JNI global reference only after the call has returned (the JNI shim holds a read lock around every callback, takes the write lock to release, and gives each init its own host record rather than process globals); a `SaveRelay` the library refused never releases the host in use. Swift keeps the callback box in a process-wide slot that only a later accepted `SaveRelay` replaces, so releasing or deallocating a `SaveRelay` can never free memory the library still calls; `isReady` says whether the library accepted an instance.
- **Service-neutral:** the calls are the same whichever service the device is signed in to or set up for: Dropbox, Nextcloud or Google Drive (see "Nextcloud and Google Drive sources").
- **Saves folders:** the C functions (plan, download and the compatibility download) fill the engine's `Options::protected` with every saves folder the library's remembered games name on this platform (`gamefiles::saves_folders`: the records `save_relay_push` and `save_relay_pull` keep), so `state_dir` can never be, hold or sit inside one, and `dest_dir` can never be or sit inside one (`destination_conflict`, before any request). `dest_dir` may hold a saves folder (a port keeps saves in `<game>/user`): then the engine reads the manifest and refuses (`destination_conflict`, before any write) when a manifest path, compared by the manifest's own case and Unicode fold, is in or above that saves folder. Paths fold case on Windows, Apple and Android (shared storage is case-insensitive). A record that cannot be read refuses the call the same way. A saves folder the library has never been told about cannot be checked: a host must not pass one.
- **Errors:** `error.class` is `retryable`, `not_yet_uploaded`, `reauth_needed` or `fatal`; `busy` is `retryable`. A provider identity change is code `remote_changed` (class `retryable`); there is no other code for it.
- **HTTP callback:** every request is a bounded range through the app's `http` callback, which must send `Range` and `If-Match`, return the 206 with its `Content-Range`, `ETag` and `Dropbox-API-Result` untouched, use identity encoding and read at most `max_response_bytes + 1` bytes (a longer answer is refused as too large, never retried); it holds one chunk (4 MiB by default), never a file.

Mobile OS background execution is not guaranteed: the next launch resumes from the last durable checkpoint. Tests can make the C functions ask for a smaller chunk (`ffi::set_game_files_chunk_for_tests`, hidden) so a small fixture spans several chunks.

## ACNH compatibility and migration

The existing reference at ACNH-Universal main `4529d152`, `android/java/io/github/acnhrecomp/GameDownload.java` and `tools/stage_dropbox_game.sh`, uses Dropbox App-folder root `/acnh-universal-game/android`, with `manifest.json` (`version`, `files`, each `path`, `size`, `sha256`) and payload paths directly under that root. Its private `gamedata/` contains an installed manifest, while `gamedata.partial/` contains partial files, `started.txt` and `verified.txt`. It resumes by Range, fetches files under 16 MiB in parallel and larger files serially, and retains `user/`, `config.ini` and logs. The Android app owns the foreground service and scheduling; the shared core does not port that service. There is no iOS downloader in that checked tree.

A host-controlled, allowlisted legacy mapping preserves the remote root and accepts this manifest shape (`version`, `files[path, size, sha256]`, no `app_id`; the Linux port adds `build_id`, `nx_game_abi` and per-file `exec`). `Layout::legacy_universal(app, HostOs)` builds the root `<app>-universal-game/<os>` (ACNH: `acnh-universal-game/android`): `app` is a lowercase letters-and-digits name joined by single hyphens, and `<os>` is one of `android`, `ios`, `linux`, `macos`, `windows`, taken from the host (`HostOs::current()` or a validated token), never from a manifest. It must preserve the player's `user/`, `config.ini` and logs, and reject a manifest naming those locations (also under `root/`). Reuse an existing final file only after rehashing it against the current manifest; legacy manifest and `verified.txt` are hints, not proof of current bytes. Legacy partials have no durable provider identity checkpoint, so do not append to them as though they were the new format; a separately tested migration may safely revalidate or restart them. Leave the legacy installer state untouched until adoption succeeds. Small-file concurrency is an optional later optimization; any concurrency must maintain aggregate memory bounds, a single destination lock and per-file checkpoints. A whole-install readiness marker is written durably only after all files are verified and published. Updating files already owned by a prior manifest needs an explicit, recoverable ownership and replacement protocol before enabling it; until then stop on conflicts and preserve existing player data.

## Verification gates

Unit tests reject invalid/colliding paths and manifests and exercise durable recovery at each write/checkpoint/publish boundary, no-replace and symlink races, pause/cancel, offline and auth errors, and hash/size mismatch. Shared fake-provider contract tests check bounded requests, offset/length/total, malformed 206, 200, 416, changed identity, short chunks and restart for all three providers. Real account checks must independently establish range and identity behavior, Drive per-file access, and actual mobile termination/restart and filesystem durability; fake tests are not evidence of those device or service results. No proprietary files are used in tests.

## What is implemented

Code: `src/gamefiles/{mod,manifest,engine,fsx}.rs`, the `GameSource`s in `src/dropbox.rs`, `src/webdav.rs` and `src/gdrive.rs`, `save-relay game-files` in `src/cli/game_files.rs`, `save_relay_game_files_plan`, `_download`, `_progress`, `_cancel` and `_cleanup` in `src/ffi.rs` (header, `bindings/ios/SaveRelay.swift`, `bindings/android`). Tests: `tests/gamefiles_manifest.rs`, `tests/gamefiles_engine.rs` (in-memory source: resume, torn and corrupt parts, hash mismatch, changed revision, range contract, conflicts, retry, one writer), `tests/gamefiles_http.rs` (real sockets and the real transport against a local server that serves Dropbox-shaped `Range` downloads, including a process abort in the middle of a file followed by a resume), `tests/ffi_game_files.rs` (the C functions end to end: a cancel held mid-file by a gated transport and resumed from the `.part`, overlapping download, cancel, cleanup and init calls, progress per run), `tests/ffi_bindings.rs` (header, JNI shim, Kotlin and Swift agree).

What it does, and where it differs from the plan above:

- **Layout:** `game-files/<app-id>/manifest.json` and `game-files/<app-id>/files/<path>` in the App folder, as designed. A port that needs a platform in the name puts it in the app id (`uncharted-1-ios`). The shared owner comment on #305 suggested `game-files/<game-id>/<platform>/`; the app-id form keeps one rule.
- **Manifest v1:** strict as written (4 MiB, no unknown fields or duplicate keys, path rules, case-fold and file/folder collisions). A manifest SHA-256 identifies the session.
- **Ranges:** every request is `Range: bytes=a-b` for at most one chunk and the read is bounded to that size. `engine::validate` accepts only the single-part, identity-encoded 206 that starts at the offset, ends inside the request, reports the manifest's size and carries exactly the bytes it claims. A 200, a 416, a bad or missing `Content-Range` is `range_unsupported`; a different total is `remote_changed`. The chunk is 4 MiB by default (the plan said 1 MiB "initially"; a 10 GB file at 1 MiB is ten thousand fsyncs) and at most 32 MiB; the host's `http` callback therefore holds one chunk in memory, never a file.
- **Identity:** the Dropbox `rev` from each answer's `Dropbox-API-Result` header is stored with the checkpoint. A different `rev` stops before the chunk is appended (`remote_changed`) and discards that file's partial, so the next run restarts it (retryable). An answer without a `rev` cannot extend bytes that have one, and the reverse, so either restarts the file too. Only the final size and SHA-256 permit publication. Nextcloud and Drive: see "Nextcloud and Google Drive sources" below.
- **Checkpoint:** state folder `.save-relay-state` (ownership marker), `session.json` (service, app id, destination, manifest digest, `ready` once every file is published), and per file in progress `parts/<id>.part` plus `parts/<id>.json` (size, SHA-256, provider identity, durable offset), `<id>` the first 32 hex of SHA-256 of the path. After every chunk: write at the offset, `fsync` the part, then an atomic write of the checkpoint (`<name>.tmp`, synced, renamed over, folder synced). A restart cuts the part to the durable offset, so unsynced or torn bytes are never kept. A file that fits one chunk writes no checkpoint (a crash re-fetches it). A kill loses at most the chunk in flight.
- **Corrupt partials:** the finished part is hashed whole. A mismatch after resuming discards it and re-fetches that file once from byte 0; a mismatch on a fresh download is `integrity_failed`. A part shorter than its checkpoint, a part that is a link or folder or has a second name (hard link count above 1), a checkpoint for other bytes (the manifest changed) or for another service is discarded.
- **No-follow traversal (`src/gamefiles/fsx.rs`):** every destination and state path is reached one component at a time through directory handles that never follow a link: `openat`/`mkdirat`/`renameat2` with `O_NOFOLLOW` on Unix (folders above a root crossed with `O_PATH` on Linux and Android), and on Windows each component opened with `FILE_FLAG_OPEN_REPARSE_POINT`, a reparse point refused, and every folder handle held without `FILE_SHARE_DELETE`. Residual Windows risk: a file leaf is opened by path, so a process already able to write in the app-private folders could swap it for another regular file between check and use (never for a link).
- **Publication:** the part's checkpoint is removed and synced first, then the part is moved into place with a no-replace rename (`RENAME_NOREPLACE`/`RENAME_EXCL`, a hard link where the file system lacks it; `MoveFileExW` without replace on Windows); an existing name is never replaced. A manifest entry with `exec` gets mode 0755 on Unix through the open handle, at publication and when an existing file is adopted. A file already in the destination is adopted only if its size and SHA-256 match the manifest; anything else is `destination_conflict` and is left as it is. Updating a file this library installed earlier is therefore a conflict until the update protocol is designed.
- **State ownership:** the library deletes in a state folder only when it carries the `.save-relay-state` marker, or is empty, or holds nothing but this library's names (`lock`, `parts`, `session.json`, its `.tmp`) with a valid session or only `parts/<id>.part`, `.json` and `.json.tmp` (folders made before the marker; the marker is then written). Anything else is `destination_conflict` and nothing in it is touched; cleanup removes only those names.
- **One writer:** an OS file lock on `state_dir/lock` (`busy`, retryable). `dest_dir` and `state_dir` must be separate folders; neither may hold the other, nor hold or sit inside a folder in `Options::protected` (the saves folders) in the case of `state_dir`; `dest_dir` may be neither one nor inside one, but may hold one when no manifest path lands in or above it. Parts live in `state_dir`, so both must be on one volume (checked by device, `destination_conflict` otherwise).
- **Control:** `cancel` stops after the chunk in flight is durable and the download returns state `cancelled`; calling download again continues (the full contract is under "Control and ABI plan"). Cleanup (`save_relay_game_files_cleanup`) removes only `state_dir` staging. There is no separate `paused` state: a cancel is resumable.
- **Errors:** the envelope's `error.class` (game-files commands only) is `retryable` (dropped connection, `429`/5xx, `busy`), `not_yet_uploaded` (the manifest or a file is not in the service folder yet), `reauth_needed` or `fatal`. New codes: `range_unsupported`, `remote_changed`, `integrity_failed`, `destination_conflict`, `busy`, `not_yet_uploaded`. A request that fails retryably is retried with a 1, 2, 4 ... 30 s wait, up to 5 times, and a request that succeeds starts the count again. A service's `Retry-After` (Dropbox 429/5xx) is carried in the error and the engine waits at least that long (at most 60 s), in the same stop-aware wait. `remote_changed` is one code with two classes, so a host decides by `class`, not by code: a changed revision is `retryable` (the next run restarts that file), a total size that differs from the manifest is `fatal` (a rerun reads the same answer).

Not done, on purpose or by limit: files are fetched one at a time (no six-way small-file parallelism); the Windows leaf residual risk above; a Kotlin or Swift way to choose `Layout::legacy_universal` (the legacy root is Rust API and `--legacy-root` only); any real-account, device or kill-by-the-OS run (the tests use a local server and `abort()`); the Dropbox and Drive 206 behaviour is taken from their documentation until a real account check.

## One engine: layouts, legacy mode, compatibility functions (#309 step A1)

`src/gamefiles/` is the only download engine. The main-line duplicate (#324) is retired; `src/game_files.rs` keeps only its two public shapes as wrappers.

- **Layout** (`gamefiles::Layout`, an engine option chosen by host code, never by a remote manifest): `Standard` (`game-files/<app-id>/manifest.json`), `Legacy { root }` and `Inline { manifest, prefix }`.
- **Legacy mode** (`manifest::parse_with(.., Mode::Legacy { root })`, Rust API only): accepts a manifest without `app_id`, binds the caller's app id and the fixed root into the manifest digest, and refuses `logs` and `manifest.json` in addition to the device-owned paths every layout refuses. It does not change any other path rule.
- **Compatibility functions:** `save_relay_download_game_files` and `save_relay_game_files_status` keep their signatures and envelope commands (`game-files`, `game-files-status`). Their manifest is inline (`game_id`, optional `remote_root`, `files`); files are fetched from `game-files/<game_id>/<path>` or `remote_root`; state sits in `<dest>/.save-relay-game-files/`. Behaviour changes from #324: an existing file that does not match is a `destination_conflict` (no overwrite), `.part` files from #324 are ignored, `remote_root` must be a relative path, an invalid manifest (a 63-character `sha256`, an unsupported version) answers `manifest_invalid` (class `fatal`) where #324 answered `usage`, and `game_id` must be a lowercase app id (`[a-z0-9][a-z0-9._-]*`, at most 128 bytes; #324 took any relative name, so a game id such as `MyGame` or `vendor/game` is now refused). The download is also stopped by `save_relay_game_files_cancel` (it returns with `complete` false).
- **Hardening:** at most 100,000 files, size sums checked for overflow, Unicode (NFD/NFKD) and full case-fold collisions and prefix collisions, reserved device names in any case or width (including `COM0`/`LPT0`, superscript digits, `CONIN$`/`CONOUT$`), device-owned paths refused in every layout, lowercase hex digests only (the compatibility manifest lowercases first).
- **Service seam:** `service::open_game_source` returns a `Box<dyn GameSource>` for the configured service: `WebDav` with the app password, `Dropbox` or `Drive` with the stored refresh token. No stored sign-in is `not_set_up`.
- **FFI:** the host's `http` response is refused before it is copied when it is larger than the request's `max_response_bytes`, and the refusal is recorded: the request fails as too large (`range_unsupported` for a range, `manifest_invalid` for the manifest), never as a retryable dropped connection, whatever the callback returns. The host reads at most `max_response_bytes + 1` bytes and hands them over.

## Nextcloud and Google Drive sources (#309 step A2)

Both implement `GameSource` (`src/webdav.rs`, `src/gdrive.rs`) over the existing save-sync clients' credentials and transport; the save-sync `Remote` trait is unchanged. `GameSource::fetch_matching` passes the identity of the file's earlier chunks (kept in the checkpoint, so also after a restart); a source that answers `remote_changed` there is not retried, and the engine discards that file's partial. Every range request asks for `bytes=a-b` with `Accept-Encoding: identity` and bounds the answer to `max(chunk, 64 KiB)` (`gamefiles::range_response_bound`; the floor lets a small error body be classified, and `engine::validate` still checks the exact 206 length). The manifest read is bounded to 4 MiB; longer is `manifest_invalid`.

- **Nextcloud (WebDAV):** `GET` on the account's files root with `Range`. The identity is the answer's strong `ETag`; later and resumed chunks send it as `If-Match`, and a 412 is `remote_changed`. A weak (`W/`) or missing ETag is not an identity: no `If-Match` is sent and a change mid-file is caught only by the `Content-Range` total and the final SHA-256. 401/403 is `auth_failed` (class `reauth_needed`), 404 is `not_yet_uploaded`, 429/5xx is retryable, a 200 to a range (whole body within the bound, or refused by the bound) is `range_unsupported` and never appended.
- **Google Drive:** each request resolves the path from My Drive's root afresh, one `files.list` per segment, at most 16 pages of at most 256 KiB each; two children with one name fail (`fatal`, the message names the path) instead of save sync's oldest-wins pick; a folder or a missing segment is `not_yet_uploaded`. Under `drive.file` a file the app may not see does not appear in a listing, so it is also `not_yet_uploaded`, and on Drive that message adds that Drive may be hiding the file (one uploaded through Drive's web site or desktop app is not given to the app; there is no picker flow yet). A non-rate-limit 403 is `fatal` and its message follows Drive's reason: an access reason says the app reads only files it created or was given, `cannotDownloadAbusiveFile` says Drive flagged the file (`acknowledgeAbuse` is never set), `fileNotDownloadable` names a Docs-type file, `downloadQuotaExceeded` and download policies say so. A Google Docs, Sheets or Slides file (`application/vnd.google-apps.*`) is refused before any media request. The scope is not widened. The identity is `<file id>:<version>`; a missing or zero version is refused (`fatal`), never taken as 0. Media is `files.get?alt=media` with `Range`; before the request a resumed or later chunk whose file now has another id or version is `remote_changed` (no media request is sent), and a metadata check after each chunk turns a changed version or size into `remote_changed` before the chunk is appended. This does not bind the media bytes atomically to the version; the final SHA-256 does. A chunk costs (path segments + 2) requests. 401 is refreshed once, then `reauth_needed`; Game-file requests are not retried inside the client (no sleeps there): a 429, a 5xx or a rate-limit 403 comes back at once as a retryable error carrying its `Retry-After`, and the engine's stop-aware retry owns the waiting (a rate-limit 403 reports `drive: HTTP 429 (rate limited)`). `downloadQuotaExceeded` is `fatal` and is not retried automatically. A status decides the class only right after a known prefix (`dropbox `, `drive: HTTP `, `webdav `, ...), so digits in a path or name never make an error retryable.

Tests: `tests/gamefiles_providers.rs` runs one contract against `Dropbox`, `WebDav` and `Drive` through their HTTP layers over a scripted transport that enforces `max_response_bytes` like the real one: full download with no byte sent twice, resume after dropped connections and after a cancel, short valid 206s, 200 to a range (large and small file), malformed and multipart `Content-Range`, wrong total, 416, identity change mid-download and across a restart, auth failure, missing manifest and file, oversize manifest, and that every request is bounded; plus 429, 503 and (Drive) rate-limit and other 403 answers on listing and content requests, names with a space, a non-ASCII character, `%` and an apostrophe, a file trashed mid-download, Nextcloud weak ETags and Drive duplicates (also named like a status), missing versions, folders, Docs-type files and endless listings; `src/ffi.rs` checks an over-bound answer through the app callback. `tests/gamefiles_nextcloud_live.rs` (ignored; run by the CI `integration` job's Linux leg against its Nextcloud container, skipped with a message when `SR_WEBDAV_*` is unset) checks 206 answers, the strong ETag and a 412 on a wrong `If-Match` against a real server. Not covered: a real Drive account (per-file `drive.file` access, real 206 and `version` behaviour), a real Dropbox account, servers other than Nextcloud 33 for If-Match on GET.

## Command line (#310)

```text
save-relay game-files plan     <app-id> --dest <dir> --state <dir> [--legacy-root <root>] [--json]
save-relay game-files download <app-id> --dest <dir> --state <dir> [--chunk <bytes>] [--retries <n>] [--legacy-root <root>] [--json]
save-relay game-files cleanup  --state <dir> [--json]
```

The commands use the service and credential store `setup` chose (`service::open_game_source`): Dropbox, Nextcloud or Google Drive; a service without its stored sign-in is `not_set_up` (exit 4). Envelopes are the C interface's (`game-files-plan`, `game-files-download`) plus `game-files-cleanup` (`data.cleaned`); failures carry `error.class`. `download`'s `data` is the final progress plus `downloaded_files`, `skipped_files` and `bytes_fetched`. Without `--json`, `download` prints a progress line per file and per five percent of the bytes, then one result line.

- **Folders:** `--dest` and `--state` are refused with `destination_conflict` (exit 1, before any request or write) when `--state` is, holds or sits inside a saves folder this machine syncs (every remembered game's), or `--dest` is or sits inside one (a `--dest` may hold a saves folder: the engine then refuses a manifest with a path in or above it), when either overlaps this program's config or data folder, or when either holds the other; paths are made absolute and resolved through links first. `download` and `cleanup` also refuse a `--state` that holds anything but the engine's own names (`engine::is_state_name`, `engine::is_part_name`: the marker, `lock`, `session.json`, `parts/<id>.part` and `.json`, and their `.tmp`): `parts` must be a real folder (not a link or junction) and every other name a plain file, so a game folder, a home folder or a folder named `parts` is never swept. `--dest` and `--state` must be on one drive or volume (a finished file is moved from the state folder). A `..` after a link is read as the file system reads it, and a remembered game that cannot be read refuses the command, so the check never passes by not looking. These are early refusals with the engine's codes; the engine stays the authority and judges the same folders again (the saves, config and data folders go into `Options::protected`; ownership by marker or adoption as above).
- **Ctrl-C:** the first stops after the chunk in flight is durable and exits 7 with `data.state` `cancelled`; run the same command to continue. A second ends the process at once, and the checkpoint on disk is still good. A request already blocked on the network finishes (or times out) first.
- **`--legacy-root`:** an explicit, relative, validated remote folder (`acnh-universal-game/android`) that selects `Layout::Legacy`; never read from a manifest. `--retries` (0 to 10, default 5) sets the engine's retries of one request.
- **Exit codes:** as `docs/code-map.md` (usage and `manifest_invalid` 2, `not_set_up` 4, network and `range_unsupported`, `not_yet_uploaded` 5, `destination_conflict` and `busy` 1), plus 7 for a Ctrl-C stop.
