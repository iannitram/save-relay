# Installer hub: game-file downloads (design)

Status: **Dropbox implemented for the mobile C interface** (#305, for Uncharted-Universal#523): `src/gamefiles/` is the core, `Dropbox` is the first `GameSource`, and `save_relay_game_files_*` in `include/save_relay.h` (with the Swift and Kotlin wrappers) is the interface. Nextcloud and Google Drive sources, a CLI command, the legacy ACNH mapping, pause as a state apart from cancel and handle-based sessions (#309, #310) are not built; see "What is implemented" at the end. Save Relay remains the save-sync application; the planned installer also downloads the user's prepared app or game files. A thin game app asks before starting the download. No game data, account credentials or private manifests belong in this repository, a release, or a public server.

## Scope and layout

Use the service and credential store already configured on this machine: Nextcloud, Dropbox or Google Drive. No second sign-in or wider OAuth scope is required by this design. Asset operations are independent of save sync, its revisions, retention, conflict resolution and locks. The service files root contains the existing configured save root and a separate `game-files/<app-id>/` tree. Never interpret a save tree as assets or delete or overwrite save data. For explicitly configured legacy apps, an app-supplied trusted mapping may instead select a fixed provider-relative root and put files directly beneath it; never accept that root from a remote manifest. An app ID is a single portable identifier (`[a-z0-9][a-z0-9._-]*`, at most 128 ASCII bytes, excluding `.` and `..`). Each app has a manifest `game-files/<app-id>/manifest.json` and its payload files below `game-files/<app-id>/files/`. The owner prepares and makes these files accessible; this design does not implement upload, discovery, piracy distribution, or public hosting.

Dropbox confines access to its registered App folder. Nextcloud uses the configured account's WebDAV files root and app password. Google Drive retains `drive.file`: the app can access files it created or that the user explicitly opens or shares with it via a supported picker. Merely putting files in My Drive, or granting access to a folder, must not be assumed to grant access to each existing descendant. An ingestion/upload or per-file picker flow for Drive is future work; until it exists, only already accessible files can be downloaded. No broad Drive scope is implied. Duplicate names or inaccessible/ambiguous paths fail visibly rather than picking an arbitrary file. [Google scope documentation](https://developers.google.com/workspace/drive/api/guides/api-specific-auth) and [desktop/mobile Picker](https://developers.google.com/workspace/drive/picker/guides/desktop-mobile-picker) describe the access boundary.

## Manifest v1

UTF-8 JSON, bounded to 4 MiB before parsing, strict fields and no duplicate JSON keys. Example (illustrative digest only):

```json
{"version":1,"app_id":"example-game","files":[{"path":"data/example.bin","size":3,"sha256":"ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"}]}
```

`version` is integer 1, `app_id` equals the requested ID, and `files` is a nonempty array of at most 100,000 entries. `size` is an unsigned 64-bit integer; reject total-size overflow. `sha256` is exactly 64 lowercase hexadecimal characters of the complete file. Paths are nonempty UTF-8 relative `/`-separated names, at most 4096 bytes overall and 255 bytes per segment. Reject empty segments, `.`, `..`, backslash, NUL and control characters, absolute paths, drive prefixes, Windows reserved names and characters, trailing dot/space, reserved installer metadata names, duplicate paths, case-folding collisions on case-insensitive targets, and file/directory prefix collisions. Reject unknown fields and versions. The manifest itself must come from the configured service at the specified path, and its SHA-256 of exact bytes identifies a session; no manifest may specify another URL or filesystem root. For the explicitly configured ACNH legacy mapping only, accept its version-1 manifest without `app_id`, binding the supplied app ID and fixed root into the session identity; apply all the same validation to its file entries. A manifest hash verifies consistency during resume, not publisher authenticity. The owner must trust the source and prepared hashes.

## Range and identity contract

Use bounded chunks (initially 1 MiB maximum), never `Remote::get` for payloads. Extend the remote seam with a bounded range operation returning bytes plus total length and representation identity. Each HTTP request requests `bytes=start-end` and bounds response reading to the chunk limit, including when the server ignores Range. The host mobile transport must honor that bound too. Accept only an identity-encoded, single-part 206 whose `Content-Range` begins at the requested offset, ends within the request, reports the exact manifest size, and agrees with the actual nonzero body length. Reject 200, malformed/missing ranges, multipart, unexpected encoding, 416 before completion, mismatched size or excess data without appending. A smaller valid contiguous 206 is acceptable and advances only by its verified length. Empty files need no range request and are verified against the empty hash. Provider errors must not leak credentials or response bodies.

Bind each file to the provider identity observed at the start and across restart: compare Dropbox revision returned in every download response; send Nextcloud a strong ETag with `If-Match`; compare Drive file ID and version before and after each chunk. A detected change stops with `remote_changed` before that chunk is appended. These checks do not prove that a representation never changed during a request: in particular a WebDAV ETag may repeat, and Drive metadata checks do not atomically bind media bytes. Therefore only exact final size and SHA-256 against the trusted manifest permit publication; a mixed or altered file fails integrity verification and is never installed. Resume requires the same observed identity, but identity alone is not an integrity guarantee. Drive revision-specific media reads can pin a revision only when it is retained as Keep Forever; do not require this for ordinary files. Drive blob downloads use `files.get?alt=media` and Range; Workspace exports do not support partial download. Nextcloud WebDAV uses HTTP GET and Range; servers ignoring or not supporting it fail as `range_unsupported`, never download an unbounded body. Dropbox content downloads use HTTP Range and their result metadata. See [Google downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [Nextcloud WebDAV operations](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html), [Dropbox content-download semantics](https://www.dropbox.com/developers/documentation/http/documentation#files-download), and [HTTP range semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests).

## Destination, checkpoint and publication

The caller supplies an app-private destination and a separate app-private state directory; neither can be the save directory or overlap the other. The core validates paths before any write and traverses directories without following symlinks or reparse points, including during creation and publication. This requires directory-handle-relative no-follow operations or an equivalent platform guarantee that prevents replacement races; a check followed by ordinary path-based open is insufficient. Refuse unsupported platforms safely. Refuse existing unrelated destination files and directories where ownership is not established; never overwrite them. Installer-owned completed files are skipped only after streaming size and hash verification. Replacement of an older installer-owned file needs an explicit update design; v1 reports a conflict instead of overwriting it.

Store each partial in the same filesystem as its eventual final file, in an installer-owned staging directory with collision-resistant names, exclusively created and never following links. A durable session record binds service/account identity without storing tokens, app ID, destination identity, exact manifest digest, each file's expected size/hash, provider identity and last durable offset. Serialize one writer per destination with an OS-backed lock held for the session; a crash releases it. No public API accepts arbitrary state or part paths. After each chunk, write at the expected offset, flush and fsync the part, then atomically write/fsync the checkpoint and parent directory. On restart truncate any bytes beyond the recorded durable offset, revalidate the record, path and provider identity, and hash the staged prefix before continuing. A crash between data sync and checkpoint may re-download at most one chunk; zero wasted bytes cannot be guaranteed. A record ahead of durable data, oversized part, missing identity, manifest change or invalid metadata fails closed rather than appending.

Once all bytes are present, stream SHA-256 over the whole part and compare exact size and digest. Fsync the part; publish using an atomic **no-replace** operation on the same filesystem, fsync the parent directory, then durably mark completion. If power fails after publication but before checkpoint, recovery verifies the final file before marking complete. Never remove or replace an unrelated final file. Keep partials on recoverable failures or pause; explicit cancel leaves completed files and removes only verified session-owned staging when the caller requests cleanup. Recheck existing completed files on every restart; a mismatch is a conflict, not an invitation to overwrite.

## Control and ABI plan

The portable Rust core owns a session with one bounded `step` at a time, reporting app ID, state, completed/total files, durable/total bytes and current relative path. States are `ready`, `running`, `paused`, `complete`, `cancelled`, `error`; resume creates or reopens a matching durable session. Pause takes effect between chunks, after durable checkpointing. Cancel and cleanup are explicit; concurrent operations on one session return busy. Network interruption is retryable without discarding the checkpoint. Distinguish `reauth_needed`, `offline`, `range_unsupported`, `remote_changed`, `integrity_failed`, `manifest_invalid`, `destination_conflict`, `io` and `busy`; do not log tokens or private content.

#310 will define and implement versioned C ABI functions and Swift/Kotlin wrappers over this core; none are exported today. Proposed calls are start/resume with app ID and host-approved destination, step/poll, pause, cancel/cleanup and close. Each returns the existing JSON envelope, with an opaque session handle owned by the library and one explicit free operation for returned memory. Host callbacks already supply transport and credentials; future requests must carry and enforce the bounded response limit. Calls may block for one chunk, so wrappers run them off UI threads. Define handle lifetime, thread affinity, callback ownership, cancellation and host background scheduling in #310; closing a handle must never erase resumable state. Mobile OS background execution is not guaranteed: the next launch resumes from the last durable checkpoint.

## ACNH compatibility and migration

The existing reference at ACNH-Universal main `4529d152`, `android/java/io/github/acnhrecomp/GameDownload.java` and `tools/stage_dropbox_game.sh`, uses Dropbox App-folder root `/acnh-universal-game/android`, with `manifest.json` (`version`, `files`, each `path`, `size`, `sha256`) and payload paths directly under that root. Its private `gamedata/` contains an installed manifest, while `gamedata.partial/` contains partial files, `started.txt` and `verified.txt`. It resumes by Range, fetches files under 16 MiB in parallel and larger files serially, and retains `user/`, `config.ini` and logs. The Android app owns the foreground service and scheduling; the shared core does not port that service. There is no iOS downloader in that checked tree.

A host-controlled, allowlisted legacy mapping preserves the remote root and accepts this manifest shape. It must preserve the player's `user/`, `config.ini` and logs, and reject a manifest naming those locations. Reuse an existing final file only after rehashing it against the current manifest; legacy manifest and `verified.txt` are hints, not proof of current bytes. Legacy partials have no durable provider identity checkpoint, so do not append to them as though they were the new format; a separately tested migration may safely revalidate or restart them. Leave the legacy installer state untouched until adoption succeeds. Small-file concurrency is an optional later optimization; any concurrency must maintain aggregate memory bounds, a single destination lock and per-file checkpoints. A whole-install readiness marker is written durably only after all files are verified and published. Updating files already owned by a prior manifest needs an explicit, recoverable ownership and replacement protocol before enabling it; until then stop on conflicts and preserve existing player data.

## Verification gates

Unit tests reject invalid/colliding paths and manifests and exercise durable recovery at each write/checkpoint/publish boundary, no-replace and symlink races, pause/cancel, offline and auth errors, and hash/size mismatch. Shared fake-provider contract tests check bounded requests, offset/length/total, malformed 206, 200, 416, changed identity, short chunks and restart for all three providers. Real account checks must independently establish range and identity behavior, Drive per-file access, and actual mobile termination/restart and filesystem durability; fake tests are not evidence of those device or service results. No proprietary files are used in tests.

## What is implemented (Dropbox, first slice)

Code: `src/gamefiles/{mod,manifest,engine}.rs`, `Dropbox`'s `GameSource` in `src/dropbox.rs`, `save_relay_game_files_plan`, `_download`, `_progress`, `_cancel` and `_cleanup` in `src/ffi.rs` (header, `bindings/ios/SaveRelay.swift`, `bindings/android`). Tests: `tests/gamefiles_manifest.rs`, `tests/gamefiles_engine.rs` (in-memory source: resume, torn and corrupt parts, hash mismatch, changed revision, range contract, conflicts, retry, one writer), `tests/gamefiles_http.rs` (real sockets and the real transport against a local server that serves Dropbox-shaped `Range` downloads, including a process abort in the middle of a file followed by a resume), `tests/ffi_game_files.rs` (the C functions end to end).

What it does, and where it differs from the plan above:

- **Layout:** `game-files/<app-id>/manifest.json` and `game-files/<app-id>/files/<path>` in the App folder, as designed. A port that needs a platform in the name puts it in the app id (`uncharted-1-ios`). The shared owner comment on #305 suggested `game-files/<game-id>/<platform>/`; the app-id form keeps one rule.
- **Manifest v1:** strict as written (4 MiB, no unknown fields or duplicate keys, path rules, case-fold and file/folder collisions). A manifest SHA-256 identifies the session.
- **Ranges:** every request is `Range: bytes=a-b` for at most one chunk and the read is bounded to that size. `engine::validate` accepts only the single-part, identity-encoded 206 that starts at the offset, ends inside the request, reports the manifest's size and carries exactly the bytes it claims. A 200, a 416, a bad or missing `Content-Range` is `range_unsupported`; a different total is `remote_changed`. The chunk is 4 MiB by default (the plan said 1 MiB "initially"; a 10 GB file at 1 MiB is ten thousand fsyncs) and at most 32 MiB; the host's `http` callback therefore holds one chunk in memory, never a file.
- **Identity:** the Dropbox `rev` from each answer's `Dropbox-API-Result` header is stored with the checkpoint. A different `rev` stops before the chunk is appended (`remote_changed`) and discards that file's partial, so the next run restarts it. Only the final size and SHA-256 permit publication.
- **Checkpoint:** state folder `session.json` (service, app id, manifest digest, `ready` once every file is published), and per file in progress `parts/<id>.part` plus `parts/<id>.json` (size, SHA-256, rev, durable offset), `<id>` the first 32 hex of SHA-256 of the path. After every chunk: write at the offset, `fsync` the part, then an atomic write of the checkpoint (`craft-atomic`). A restart cuts the part to the durable offset, so unsynced or torn bytes are never kept. A file that fits one chunk writes no checkpoint (a crash re-fetches it). A kill loses at most the chunk in flight.
- **Corrupt partials:** the finished part is hashed whole. A mismatch after resuming discards it and re-fetches that file once from byte 0; a mismatch on a fresh download is `integrity_failed`. A part shorter than its checkpoint, a part that is a link or folder, a checkpoint for other bytes (the manifest changed) or for another service is discarded.
- **Publication:** an atomic no-replace hard link from the verified part, then `fsync` of the folder and removal of the part (a rename after an existence check where links are unavailable). A file already in the destination is adopted only if its size and SHA-256 match the manifest; anything else is `destination_conflict` and is left as it is. Updating a file this library installed earlier is therefore a conflict until the update protocol is designed.
- **One writer:** an OS file lock on `state_dir/lock` (`busy`, retryable). `dest_dir` and `state_dir` must be separate folders; neither may hold the other. Parts live in `state_dir`, so both must be on one file system.
- **Control:** `cancel` stops after the chunk in flight is durable and the download returns state `cancelled`; calling download again continues. Cleanup (`save_relay_game_files_cleanup`) removes only `state_dir` staging. There is no separate `paused` state: a cancel is resumable.
- **Errors:** the envelope's `error.class` (game-files commands only) is `retryable` (dropped connection, `429`/5xx, `busy`), `not_yet_uploaded` (the manifest or a file is not in the service folder yet), `reauth_needed` or `fatal`. New codes: `range_unsupported`, `remote_changed`, `integrity_failed`, `destination_conflict`, `busy`, `not_yet_uploaded`. A request that fails retryably is retried with a 1, 2, 4 ... 30 s wait, up to 5 times, and a request that succeeds starts the count again.

Not done, on purpose or by limit: files are fetched one at a time (no six-way small-file parallelism); destination folders are checked with `symlink_metadata` rather than opened through directory handles, so a hostile process already able to write inside the app-private folders could race it; Nextcloud and Google Drive sources; per-app legacy roots such as ACNH's `acnh-universal-game/android`; any real-account, device or kill-by-the-OS run (the tests use a local server and `abort()`); the Dropbox 206 behaviour is taken from its documentation until a real account check.
