## Blockers (1.0)

### B1. An empty or missing saves folder is pushed as the newest revision
- **Where:** `src/plan.rs:91-96` (`(true, false) => Push`), `src/scan.rs:95-99` (missing folder scans as an empty set), `tests/plan.rs:118-121` (locks the behaviour in).
- **What happens:** the machine last synced revision n; the saves folder then vanishes or is emptied (SD card not mounted, Proton prefix rebuilt, reinstall, wrong `--saves-dir`). Launch publishes revision n+1 with no files; every other machine pulls it and deletes its saves.
- **Ruling:** when local is empty and the server has saves, pull the server's saves. Pushing an empty set over a non-empty revision needs an explicit flag.
- **Expected:** `decide` returns Pull at launch (and not Push at exit) for an empty local set with a last-synced record and a non-empty server revision; the plan table in the doc comment and `docs/code-map.md` say so; the locked test at `tests/plan.rs:118` is replaced.
- **Musts:** M1, M9, the 1.0 sentence.

### B2. The panel never shows a pending choice, and a late answer does nothing
- **Where:** `src/sync.rs:719-721` (`pending: None`, "not read yet"); `src/local.rs:173` (`list_pending` has no caller); `panel/src/App.tsx:47-48` (reads only `status.pending`) and `:95-102`; `panel/src/actions.ts:38-47`; `src/pending.rs:148-171`; `src/wrap.rs:170-183`, `263-283`; `src/cli.rs:1631-1652`.
- **What happens:** a wrapped game hits a conflict or an open-elsewhere mark in Game Mode; `wrap` waits 120 seconds; the panel shows nothing. If the choice is answered later (for example a conflict found by the push at exit), the panel says "Recorded keep-local" and nothing is pushed or pulled; the next launch overwrites the file with a fresh unanswered choice.
- **Ruling:** a late answer is applied right away.
- **Expected:** `status --json` fills `pending` from the pending file; the panel lists it; answering while `wrap` waits works as today; answering with no `wrap` waiting runs the resolve (`pull --resolve` / the push) on the spot and clears the pending file and the badge; the banner reports what was actually done.
- **Musts:** M3, M11, M12, M15.

### B3. A wrapped game found through the ludusavi data is never remembered
- **Where:** `src/cli.rs:1317-1337` (`ludusavi_game` saves a `GameRecord` only when `--saves-dir` is given); `src/cli.rs:100-103` (`GameArg::load` then returns `GameUnknown`); `src/cli.rs:1619` (`where` uses `list_games`).
- **What happens:** after `wrap -- %command%` syncs `steam-<appid>`, there is no `games/steam-<appid>.json`. `status`, `restore` and `pull --resolve` exit 2 with `game_unknown`, and the game is missing from `where`, which is the panel's games list.
- **Expected:** the first successful locate of a wrapped game saves its record; `status`, `history`, `restore`, `where` and the panel then work for it; a manifest of the owner's own still wins.
- **Musts:** M4, M12, M15.

### B4. The Steam screenshot is not wired into a wrapped game's card
- **Where:** `src/steam.rs:193-217` (`screenshot_dir`, `pick_screenshot`: called only from `tests/steam.rs`); `src/sync.rs:356-384` (`found_in` reads only the port sidecar). `docs/code-map.md` and `src/card.rs:9` describe it as present.
- **What happens:** every wrapped game's card has `picture: null`.
- **Expected:** at push, a wrapped game with no sidecar picture gets the newest Steam screenshot of that app taken during the session, through the same size and type checks as a sidecar picture; an integration test with a fixture screenshots folder.
- **Musts:** M14.

### B5. The ludusavi data can set the saves folder to a whole home folder or a drive root
- **Where:** `src/ludusavi.rs:292-307`, `335-348` (a candidate that is an existing folder becomes `saves_dir` with include `**`); `src/manifest.rs:78-103` (`validate` checks the patterns, never the folder); effect in `src/transfer.rs:223-241`.
- **What happens:** an entry whose path is just `<home>`, `<winDocuments>`, `<base>`, `<root>`, `/` or `C:/Users` is accepted. A push then hashes and uploads everything under it; on another machine "keep server" deletes every local file there that the entry lacks. The data is community-edited and downloaded. Whether a live entry does this today was not checked.
- **Expected:** `translate` refuses (`save_location_unclear`) a folder that is a filesystem root, the home folder, or a bare platform folder (`{home}`, `{data}`, `{config}`, `{documents}`, the Steam root, a library root, a Proton prefix's user folder); unit tests with fixture entries for each. Also cap the download size (`src/http.rs:185-187` reads the body with no limit).
- **Musts:** M13 ("never guess"), Won't "a guessed saves folder".

### B6. Google Drive: day-old claim cleanup can make a game unpushable for good
- **Where:** `src/gdrive.rs:578-597` (`clean_claims`, called at 571 and 736), with `510-526`.
- **What happens:** a push dies after creating `.claim-C` (suspend, network drop), leaving `state.json` at `(V, C)`. More than a day later another machine writes `playing.json`; the put deletes `.claim-C`. Every later guarded write gets 409 on the create and 404 on the claim read, mapped to `changed_on_server`, from every machine.
- **Confidence:** traced against the repo's own Drive model (`src/fake/gdrive.rs:35-38`: a used id stays used after delete). Not checked on real Drive; add it to #47's list.
- **Expected:** `clean_claims` never deletes the claim `state.json` still names; a `fake_drive` test of the scenario above; `repair` (or the next push) can recover a game already in that state.
- **Musts:** M9.

## Should-fix before a release

### S1. WebDAV: a network drop mid-push strands the claim until `repair` is run by hand
`src/sync.rs:578-594`, surfaced at `227-233`. After `rev/<n+1>` is created and the `state.json` PUT fails as unreachable, the release is a best-effort delete over the same dead link. Every later push from any machine returns `changed_on_server`. M5 does not hold unattended. Idea: let a machine release a claim whose body names its own device.

### S2. `repair` can orphan the entry of a push that is paused, not dead
`src/sync.rs:871-904` against `584-593`. A handheld suspended between claim and state PUT wakes after another machine ran `repair`; its If-Match still passes and `state.json` names an entry now in `set-aside/`. Its failure path also deletes `rev/<n+1>` without checking whose claim it is.

### S3. `wrap` handles no signals
`src/wrap.rs:102-153`. Steam's force exit, a logout or a shutdown ends `wrap` with the game: no push, and `playing.json` stays set. (Steam's exact behaviour needs the #72 device check.)

### S4. A wrapped game cannot receive saves on a machine where it has never run
`src/ludusavi.rs:310-320`, `src/cli.rs:1239-1242`. Folders that do not exist are dropped, none left is `save_location_unclear`, and the game starts unsynced; the next launch is a conflict. When exactly one candidate folder is named and the server has saves for the game, create it and pull.

### S5. "Refuse when unclear" has holes
`src/ludusavi.rs:212-263`, `src/cli.rs:2079-2080`. Candidates with an unknown placeholder, `<storeUserId>` with two Steam users, or `<base>` with no appmanifest are dropped before the "exactly one" test, so a config folder can be reported as the clear saves folder. A leftover Proton prefix wins over a now-native game's folder.

### S6. The Decky backend kills any command at 60 seconds
`decky/main.py:15`, `91-99`. Includes `restore`, `pull` and `push`; a kill after `write_state` leaves the server on the new revision and local files old, and the panel says "timed out". On WebDAV it can strand a claim (S1), and `repair` is not a panel command.

### S7. One 60-second deadline covers a whole HTTP request, body included
`src/http.rs:141-145`. A large save on a slow uplink always times out, is treated as offline, and never reaches the server. Bodies are held in memory with no cap.

### S8. A retried conditional write after a 5xx can delete the entry `state.json` names
`src/dropbox.rs:304-312`, `430-444`; `src/gdrive.rs:329-344`, `721-734`; consequence at `src/sync.rs:584-590`. The write committed but answered 5xx; the retry sees a conflict, returns `Changed`, and the fresh entry is deleted while the server state points at it.

### S9. A failure after `state.json` is published is reported as a failed push
`src/sync.rs:236-249`; restore at `1028-1050`. History list, retention and marker pruning all run before `record_sync`; one failed DELETE leaves the mark set and the session open. Record first, prune best-effort.

### S10. Downloads are not durable or atomic as a set
`src/transfer.rs:133-137`, `215-222`. Part files are not fsynced before rename; a rename failure midway leaves a mix of two revisions and no backup of the pre-pull files.

### S11. Case-only file name differences delete the file just downloaded (Windows)
`src/transfer.rs:113-118`, `215-233`. Paths are compared case-sensitively on a file system that is not. Logic confirmed; NTFS behaviour not tested.

### S12. Different include/exclude patterns between machines silently drop files
`src/sync.rs:170-189`, `src/plan.rs:91`, `src/transfer.rs:224-233`. A machine with a narrower manifest pulls a file, does not scan it, and pushes a revision without it.

### S13. Release workflow runs third-party actions by tag in the job that can write releases
`.github/workflows/release.yml:43`, `87`, `90`, `166`, `235`. Pin to commit SHAs. `check.yml` has no `permissions:` block; `SHA256SUMS` proves integrity, not origin.

### S14. Panel token and API surface
`src/panel.rs:347-354`, `202`, `591-603`; `panel/src/main.tsx:24-25`. The token is passed in the browser-open process arguments, stays in the address bar, and is accepted from the query string on POST routes. The API accepts `push`, `saves-dir`, `manifest`, `resolve`, `root` and `setup --finish`, which the front end never sends; trim it to what the views use.

### S15. Restore in the panel has no in-flight state
`panel/src/App.tsx:176-194`. Buttons stay live, so a second press runs a second restore; an old success banner stays beside a later error.

### S16. Game Mode: B and the D-pad are swallowed when the panel has nothing to do with them
`decky/src/index.tsx:85-102`. On the Games view B does nothing and the D-pad cannot leave the panel. Check in #73.

### S17. `install-wrap` edge cases
- `src/steam/launch.rs:31-35`, `141-149`: the Linux Steam-running check trusts a bare pid; Flatpak Steam's pid file is not in the list, and `current_exe()` may not be runnable inside the sandbox.
- `src/steam/launch.rs:234-240`, `src/steam.rs:181-184`: one all-digit `userdata` folder without `localconfig.vdf` (such as `userdata/0`) aborts the whole command.
- `src/steam/launch.rs:311-328`, `47-60`: a wrap with options before `--` (as `docs/wrap.md:60` shows) is not recognised and gets wrapped twice.

## Minor

- `history` and `picture` do not validate the game id (`src/cli.rs:346-352`, `563-575`; `src/panel.rs:479`, `636`).
- The conflict loser has no lasting protection from retention (`src/sync.rs:140-155`, `240-247`).
- `restore` publishes before validating the entry's record and hashes (`src/transfer.rs:251-260`, `src/sync.rs:983-1036`).
- A WebDAV PUT answered without an ETag is treated as a failure (`src/webdav.rs:425-429`).
- An unreachable `playing.json` read counts as "no mark" (`src/sync.rs:455`).
- A stray request to the sign-in loopback listener aborts the sign-in (`src/oauth.rs:617-629`).
- A transient failure in `setup --finish` deletes the pending sign-in (`src/cli.rs:1783-1793`).
- Nextcloud setup accepts `http://` for any host without a warning (`src/webdav.rs:19`).
- `Dropbox-API-Arg` escaping misses U+007F (`src/dropbox.rs:59-73`).
- The Drive guard assumes `version` holds still after a write (`src/gdrive.rs:564-570`, `687-690`); check on real Drive in #47.
- `<winDocuments>` is hard-coded to `%USERPROFILE%\Documents` (`src/platform.rs:110`); a OneDrive-redirected Documents is missed.
- The panel server is one thread with a per-read timeout and no `catch_unwind` (`src/panel.rs:356-386`); the Game Mode timeline waits for every picture before it renders (`decky/src/index.tsx:70-78`).
- A failed `status` hides that game's pending choice (`panel/src/App.tsx:47`); non-JSON error replies show as "Unexpected token" (`panel/src/bridge.ts:39-50`); the fixture bridge ships in the release build (`panel/src/main.tsx:26`).
- `src/main.rs:6` uses `std::env::args()`, which panics on a non-UTF-8 argument.
