# Spec

**1.0 means:** I finish a chapter of Uncharted on my AMD handheld, then start Uncharted on my Strix Halo tablet or my RTX 3090 Ti desktop, and the game loads that save, with no file copying by hand; my Mac, through a signed save-relay build, and my iPhone, through an app that links the save-relay library, pull and push those same saves ("The save relay Mac and iOS functions need to be brought into 1.0", my ruling of 2026-11-17). The saves travel through the service I picked at setup: my Nextcloud, Google Drive or Dropbox. That same service holds my ports' prepared game files: a thin app on my Android phone or iPhone, or `save-relay game-files` on a desktop, downloads them in pieces, carries on where it stopped after an interruption, checks every file before using it, and never touches my saves or settings (M19; added to this sentence by my ruling of 2026-11-26). If I suspend the handheld mid-chapter instead of quitting, the desktop tells me the game is still open there before I play. Any other Steam game with a known save folder does the same with one launch option, and in Game Mode the Save Relay panel shows each game's saves as cards (picture, playtime, where I was) that I can restore with one press.

## Thin-app installer scope (owner direction 2026-11-24)

Save Relay also supplies the shared library service for Android and iOS thin apps to pull, install and resume their private prepared game-file chunks, alongside save sync. This is not an app store; the separate launcher repo is outside this implementation scope. The owner requested this extension directly on 2026-11-24 and named ACNH as the reference. It extends the earlier save-only scope without claiming the published RC already implements it.

The required services are Dropbox, Nextcloud and Google Drive, reusing the configured session and credential store. A path/size/SHA-256 manifest, bounded byte-range reads, durable partial files, verified publication, restart skipping of verified complete files, progress and pause/cancel form the shared contract (#305 -> #309 -> #310). Assets live separately from save histories and never cause save files, user settings or unrelated files to be overwritten. Preserve ACNH's existing private Dropbox layout through an explicit compatibility/migration contract. Proprietary game files stay in the owner's storage and app sandbox; none go into this repo, CI, releases or public links. Mobile apps own foreground/background scheduling. Existing Mac/iOS and save-sync acceptance requirements remain.

## Won'ts

- Syncing while the game runs; only pull at launch and push at exit (the open-elsewhere mark of M11 is written at launch and cleared at exit, nothing in between).
- Capturing the screen myself: a card's picture comes from the port or from Steam's own screenshots, or there is none.
- A guessed saves folder: a wrapped game with no clear entry is refused (M13).
- Any storage other than my Nextcloud (WebDAV), Google Drive and Dropbox; Steam Cloud.
- Moving saves from one service to another automatically: switching services starts fresh (I can push again from any machine).
- Settings or logs in save sync: saves only (a save card's small picture and text travel with the save they describe). Thin-app prepared assets use the separate installer namespace, not save history.
- A panel outside Steam's Game Mode other than `save-relay panel` in the browser (no tray app, no desktop window).
- A signed Windows binary in 1.0: it ships unsigned by owner decision, and the README covers SmartScreen; signing comes after 1.0 (owner ruling 2026-11-25, Q6).
- A Mac library asset or an Intel Mac build in 1.0 (Q5).
- A 3DS bridge in 1.0: it is After 1.0 (Q9). Its design (#300, #330) treats an automatic newest-wins pick that keeps and uploads the loser as satisfying M3.
- An app store: the installer fetches one app's own prepared files from the owner's storage; the launcher repo is outside this repo.

## Problem

My game ports keep saves in a folder on each machine. Moving from the handheld to the desktop means copying folders by hand, and I lose track of which copy is newest. Each port would otherwise grow its own sync code.

## Solution

One small library and command-line tool that every port's launcher calls: pull before Play, push after the game quits, through my own Nextcloud, with a conflict prompt, history and offline play. A game joins with a manifest. A Mac build (Apple Silicon CLI, M17) runs the same tool; iOS builds (M18) and Android builds (M20) embed the same core. Thin apps also use it to install their prepared game files (M19).

## User stories

1. As the owner, I want to continue my save on whichever machine I pick up, so that I never copy save folders by hand.
2. As the owner, I want to be asked when two machines both changed a save, so that I never lose progress silently.
3. As the owner, I want to restore an older save, so that a bad save or a wrong pick is recoverable.
4. As a port maintainer, I want to add a game with one manifest, so that every port shares the same pathway.
5. As the owner, I want to be told a game is still open on another machine, so that a suspended handheld never hides my newest save.
6. As the owner, I want any Steam game to sync with one launch option, so that the tool covers my whole library, not only my ports.
7. As the owner, I want to see where I was and how long I played in each save, so that choosing or restoring a save is obvious at a glance.

## Implementation decisions

- Rulings 2026-10-31 (question tool): Nextcloud over WebDAV with a per-device app password; pull at launch, push at exit; ask and keep both on conflict; shared library + CLI; 1.0 = Uncharted on the three PCs; last 10 versions per game; play local and push later when offline; new public repo; own small Rust core, with Ludusavi as the main peer to learn from.
- Storage is one interface with three backends: WebDAV (a create-once `rev/<n+1>` claim guards servers whose etag can repeat before push or restore writes state with If-Match; #149; a crash can strand it and `repair` releases it, moving a complete entry it names to `<game>/set-aside/`), Dropbox (uploads tied to the file revision) and Google Drive (a narrow-scope folder; its weaker overwrite check gets a guard so M9 holds). Google Drive and Dropbox sign in with OAuth in the browser (PKCE, loopback redirect); the app registrations on each service are made under my own accounts.
- Core in Rust: a library crate and a `save-relay` binary. It must build for Linux, Windows, macOS (M17), iOS (M18) and Android (M20), with no platform-only dependencies in the core.
- Server layout under one Nextcloud folder: per game, the current saves, a small state file (revision, device, time, file list with hashes), and a history folder of dated copies. Each machine records the revision it last synced; a conflict is "server revision changed and local files changed since that revision".
- Pushes upload to a temporary name and rename, so a broken upload never replaces the current saves.
- The game manifest is a small data file shipped by each port.
- The installer (M19) is one engine, `src/gamefiles/`, behind a `GameSource` seam with Dropbox, WebDAV and Google Drive sources. It reads a path/size/SHA-256 manifest, fetches bounded byte ranges into durable `.part` files with a journal, checks each file's hash and publishes it through handle-relative, no-follow, no-replace opens. Files the app marks as protected are never touched. Its files live under `game-files/`, apart from save histories (#305, #309, #310).
- Rulings 2026-11-25 (owner, coordinator session, recorded on #308):
  - Q3: the publisher (#328) is in 1.0, so Google Drive installs work under `drive.file`.
  - Q4: the desktop `save-relay game-files` command is in 1.0.
  - Q7: the two #324 C functions (`save_relay_download_game_files`, `save_relay_game_files_status`) stay as deprecated wrappers on the new engine and are removed after 1.0.
  - Q8: before the installer's C interface freezes, add an entry point that verifies and publishes a file the iOS app downloaded itself (background `URLSession`).
  - Q10: `game-files/<app>/<os>/` is the standard layout. ACNH's existing `acnh-universal-game/android` is read in place as a legacy layout, with no migration.
  - Q11: phones write the open-elsewhere mark (M11) at launch, and clear it with a successful push when the app pauses or goes to the background. A failed push leaves the mark up as a warning.
- Rulings 2026-11-01 (question tool): the Baton, `wrap` and save cards with a Game Mode panel, all in 1.0; the open-elsewhere mark "Never blocks, always asks (Recommended)"; the card picture "Port writes it, wrap grabs Steam's (Recommended)".
- The open-elsewhere mark is a small `playing.json` beside `state.json` (device, time, revision read), written at `pull` and removed at `push`; the plan table gains a row for it before Pull.
- `wrap` reuses the engine unchanged: it is `pull`, a child process, then `push`. The ludusavi-manifest data is MIT, downloaded and cached, never bundled as code.
- The panel is a Decky Loader plugin talking to the same binary's `--json`; `save-relay panel` serves the same views on loopback for the desktop. The design pass is no longer skipped.

## Testing decisions

- The sync logic (change detection, conflict decision, retention) is pure and unit-tested.
- Integration tests run the CLI against a local WebDAV server in CI, with no real Nextcloud and no real game.
- The installer's providers share one fake contract test suite (Dropbox, WebDAV and Google Drive fakes); no live account runs in CI.
- Device checks on the three PCs, the Mac, the iPhone and an Android phone, and the installer on each service, are marked `needs-owner-device`. A green fake-backed test is never recorded as device verification.
